# World 7 · Object-Oriented & Data Design

## 7.1 | Class, attribute, operation, interface | Classes, attributes, operations, interfaces
@card 07#3-4
:vi
**Class diagram** là sơ đồ UML **được dùng nhiều nhất trong thực tế**. Thành phần chính: **classes, interfaces, relationships** và **common mechanisms**.

**Class** định nghĩa **tập các object có chung attribute, operation, relationship và ngữ nghĩa**; một class **đại diện cho một "thứ"**. Ký hiệu là hình chữ nhật 3 ngăn: **tên**, **attributes**, **operations**. Tên class phải **duy nhất trong nhóm** của nó.
:en
The **class diagram** is **the most commonly used UML diagram in practice**. Main elements: **classes, interfaces, relationships** and **common mechanisms**.

A **class** defines **the set of objects that share the same attributes, operations, relationships and semantics**; a class **represents a thing**. It is drawn as a three-compartment box: **name**, **attributes**, **operations**. A class name must be **unique within its group**.

@card 07#5-6 fig=uml-class
:vi
**Attribute**: dữ liệu **mô tả đặc điểm** của class, là một trừu tượng của loại dữ liệu hay object. Ví dụ `title` là attribute kiểu `String`. **Kiểu dữ liệu viết sau dấu hai chấm** `:`.

**Operation**: một **dịch vụ có thể yêu cầu** từ các object của class, ví dụ `calcSalary(year: int): float`.

**Visibility** của attribute và operation:

| Ký hiệu | Visibility |
|---|---|
| **+** | **public** |
| **-** | **private** |
| **#** | **protected** |
:en
An **attribute** is data that **characterizes** a class: an abstraction of the kind of data or object. For example `title` is an attribute of kind `String`. The **data type follows a colon** `:`.

An **operation** specifies **a service that can be requested** from objects of the class, e.g. `calcSalary(year: int): float`.

**Visibility** of attributes and operations:

| Symbol | Visibility |
|---|---|
| **+** | **public** |
| **-** | **private** |
| **#** | **protected** |

@card 07#7
:vi
**Interface**: một phần tử có **tập các operation mô tả hành vi** của nó (không có dữ liệu riêng).

**2 cách vẽ:**
- **Một hình tròn kèm tên** (ký hiệu "lollipop").
- **Một class có stereotype `<<interface>>`**, liệt kê các operation. Ví dụ `<<interface>> Diagnosis` với `+basicExamine()`, `+takeXray()`, `+takeMRI()`.
:en
An **interface** is an element with **a set of operations characterizing its behaviour** (no data of its own).

**Two notations:**
- **A circle with a name** (the "lollipop").
- **A class with the stereotype `<<interface>>`** listing its operations, e.g. `<<interface>> Diagnosis` with `+basicExamine()`, `+takeXray()`, `+takeMRI()`.

## 7.2 | Quan hệ giữa các class | Class relationships
@card 07#8-12 fig=uml-relations
:vi
Hầu hết class đều liên quan tới class khác. **3 loại quan hệ chính:** **Dependency, Generalization, Association** (aggregation và composition là hai dạng đặc biệt của association).

| Quan hệ | Ý nghĩa | Ký hiệu |
|---|---|---|
| **Dependency** | Class này **dùng** class kia: một operation gọi operation của class khác, hoặc class kia là **tham số**. Đổi class bị dùng có thể ảnh hưởng class dùng nó. **Lỏng nhất** | Nét **đứt**, mũi tên mở |
| **Generalization** | Quan hệ giữa class **chung** (superclass) và class **cụ thể** (subclass) | Mũi tên **tam giác rỗng** chỉ vào superclass |
| **Association** | Object của class này **được nối với** object của class kia; thường một object **giữ** các object khác. Có thể có **tên** và **role** ở hai đầu | Đường **liền** |
:en
Most classes relate to others. **Three main kinds:** **Dependency, Generalization, Association** (aggregation and composition are special kinds of association).

| Relationship | Meaning | Notation |
|---|---|---|
| **Dependency** | One class **uses** another: an operation calls an operation of the other class, or the other class is a **parameter**. A change in the used class may affect the user. **Least restrictive** | **Dashed** line, open arrow |
| **Generalization** | Between a **general** class (superclass) and a **more specific** class (subclass) | **Hollow triangle** pointing at the superclass |
| **Association** | Objects of one class **are connected to** objects of another; typically one object **holds** others. Can have a **name** and **roles** at both ends | **Solid** line |

@card 07#13 fig=multiplicity
:vi
**Multiplicity**: **bao nhiêu object** có thể được nối qua một association. Trong ví dụ, association **works for** có role **+employee** và **+employer** ở hai đầu, cùng multiplicity **1..\*** và **0..\***.

Cách đọc theo chuẩn UML (slide chỉ đưa hình): số ghi ở một đầu cho biết **một object ở đầu bên kia** nối với bao nhiêu object ở đầu này. Vậy một Company có **1..\*** Person, một Person làm cho **0..\*** Company.

Các giá trị hay gặp: `1` (đúng một), `0..1` (không hoặc một), `0..*` hay `*` (bao nhiêu cũng được), `1..*` (ít nhất một).
:en
**Multiplicity**: **how many objects** may be connected across an association. In the example, the association **works for** has the roles **+employee** and **+employer** at its ends, with multiplicities **1..\*** and **0..\***.

Reading it the standard UML way (the slide only shows the figure): the number at one end says how many objects at that end **one object at the other end** links to. So a Company has **1..\*** Persons, and a Person works for **0..\*** Companies.

Common values: `1` (exactly one), `0..1` (zero or one), `0..*` or `*` (any number), `1..*` (at least one).

@card 07#14
:vi
Hai dạng association đặc biệt, phân biệt bằng **quyền sở hữu**:

| | **Composition** | **Aggregation** |
|---|---|---|
| Độ mạnh | **Strong** association | **Weak** association |
| Ý nghĩa | Class này **sở hữu** class kia và **chịu trách nhiệm vòng đời** của nó | Class này **dùng** class kia nhưng **không sở hữu** |
| Ví dụ | **University ◆— Faculty**: xoá trường thì khoa mất theo | **Faculty ◇— Lecturer**: khoa đóng cửa, giảng viên vẫn còn |
| Ký hiệu | Hình thoi **đặc** ở phía sở hữu | Hình thoi **rỗng** ở phía chứa |
:en
Two special associations, told apart by **ownership**:

| | **Composition** | **Aggregation** |
|---|---|---|
| Strength | **Strong** association | **Weak** association |
| Meaning | One class **owns** the other and **is responsible for its lifetime** | One class **uses** the other but **does not own it** |
| Example | **University ◆— Faculty**: delete the university and its faculties go too | **Faculty ◇— Lecturer**: close the faculty and the lecturers remain |
| Notation | **Filled** diamond at the owner | **Hollow** diamond at the whole |

@card 07#15
:vi
Ví dụ **class diagram "Online Shop"** trên slide gom đủ các ký hiệu:
- **Customer 1 — 0..\* Order**: association có multiplicity.
- **Order ◇— OrderDetail** (1 — 1..\*, role name **line item**): aggregation.
- **OrderDetail → Item** (0..\* — 1): association có **navigability** (mũi tên chỉ chiều đi được).
- **Payment** là **abstract class** (tên in nghiêng); **Credit, Cash, Check** là subclass qua **generalization**.
- Order có attribute `date, status` và operation `calcTax, calcTotal, calcTotalWeight`.
:en
The slide's **"Online Shop" class diagram** uses every notation:
- **Customer 1 — 0..\* Order**: an association with multiplicity.
- **Order ◇— OrderDetail** (1 — 1..\*, role name **line item**): aggregation.
- **OrderDetail → Item** (0..\* — 1): an association with **navigability** (the arrow shows which way you can navigate).
- **Payment** is an **abstract class** (italic name); **Credit, Cash, Check** are subclasses via **generalization**.
- Order has attributes `date, status` and operations `calcTax, calcTotal, calcTotalWeight`.

## 7.3 | Từ requirement đến class: domain object & BCE | From requirements to classes: domain objects & BCE
@card 07#17
:vi
**2 loại object:**

| **Domain object** | **System object** |
|---|---|
| **Thực thể ngoài đời thật** | **Thực thể được tạo ra** cho phần mềm |
| **Tham gia quy trình nghiệp vụ** | **Hỗ trợ xử lý và tính toán** |
| **Có dữ liệu cần lưu** | |
:en
**Two types of object:**

| **Domain object** | **System object** |
|---|---|
| **Real-world entity** | **Created entity** |
| **Takes a role in the business process** | **Supports processing and calculations** |
| **Has stored data** | |

@card 07#18 fig=bce
:vi
**Boundary – Control – Entity (BCE)** phân object theo vai trò:
- **«boundary»**: giao diện giữa **actor và hệ thống**: màn hình, form, **API endpoint**. Ví dụ `RegistrationUI`.
- **«control»**: **điều phối các bước của một use case**. Ví dụ `RegistrationController` cho "Register for a course".
- **«entity»**: **dữ liệu và luật nghiệp vụ sống lâu**, lấy từ domain model. Ví dụ `Course`, `Enrollment`.

**Quy tắc:**
- Boundary và control là **system object**; entity là **domain object**.
- **Actor chỉ nói chuyện với boundary**; **entity không bao giờ gọi boundary**.
- BCE khớp với **layered architecture**: presentation → business → data.
:en
**Boundary – Control – Entity (BCE)** groups objects by role:
- **«boundary»**: the interface between **actors and the system**: screens, forms, **API endpoints**. E.g. `RegistrationUI`.
- **«control»**: **coordinates the steps of one use case**. E.g. `RegistrationController` for "Register for a course".
- **«entity»**: **long-lived business data and rules** from the domain model. E.g. `Course`, `Enrollment`.

**Rules of thumb:**
- Boundary and control are **system objects**; entities are **domain objects**.
- **Actors talk only to boundaries**; **entities never call boundaries**.
- BCE maps to a **layered architecture**: presentation → business → data.

@card 07#19-20
:vi
**Bước 1: Xác định domain class.** Nguồn là **domain model** của requirement.
- **Ứng viên class = các danh từ** trong use case specification và user story. Nếu nhóm có **conceptual ERD** thì nó cho ra cùng các entity.
- **Mỗi domain entity → một entity class**: thuộc tính → **attribute**, quan hệ → **association**.
- **Chỉ giữ** class có **lưu dữ liệu** hoặc **có vai trò trong quy trình nghiệp vụ**. Bỏ class **trùng**, từ **mơ hồ**, và **attribute đội lốt class**.

Ví dụ **"Shipping System"**: ERD có CREW, CAPTAIN, VESSEL, SOTL, REGION, nên ra các domain class **Vessel, VesselType, Region, Crew, Captain**.
:en
**Step 1: identify domain classes.** The source is the requirements' **domain model**.
- **Candidate classes = nouns** in use case specifications and user stories. A **conceptual ERD**, if the team has one, gives the same entities.
- **Each domain entity → one entity class**: properties → **attributes**, relationships → **associations**.
- **Keep only** classes that **store data** or **play a role in the business process**. Remove **duplicates**, **vague words** and **attributes disguised as classes**.

Example **"Shipping System"**: the ERD has CREW, CAPTAIN, VESSEL, SOTL and REGION, giving the domain classes **Vessel, VesselType, Region, Crew, Captain**.

@card 07#19 real
:vi
Áp dụng cho BadminBookingHub: các danh từ trong use case đặt sân như **Player, Court, Booking, Deposit, Time slot** là ứng viên class. "Booking status" nghe như danh từ nhưng thực ra là **attribute** của Booking, nên không tách thành class riêng.
:en
Applied to BadminBookingHub: nouns from the booking use cases such as **Player, Court, Booking, Deposit, Time slot** are candidate classes. "Booking status" sounds like a noun but is really an **attribute** of Booking, so it does not become its own class.

## 7.4 | Sequence diagram & state machine | Sequence diagrams & state machines
@card 07#21-22
:vi
**Bước 2: Xác định system object.** Nguồn là **use case specification** (flow of events).
- **Mỗi bước trong "kịch bản" phải do một object thực hiện.** Khi không domain object nào làm được thì tạo **boundary** hoặc **control** object.
- Vẽ **sequence diagram cho mỗi scenario quan trọng**: **lifeline** cho thấy các object, **message** cho thấy operation của chúng.

**Sequence diagram** thể hiện object **tương tác theo thời gian** để thực hiện một scenario. Thành phần:

| Thành phần | Ý nghĩa |
|---|---|
| **Lifeline** | Người tham gia: actor, boundary, controller, entity object |
| **Message** | **Synchronous call**, **asynchronous message**, **return** |
| **Activation bar** | Khoảng thời gian object **đang thực thi** |
| **Combined fragment** | **alt** (if/else), **opt** (if), **loop**, **par** |

Cách vẽ: lấy **một luồng** từ use case spec, **một sơ đồ cho mỗi scenario quan trọng**; **mỗi message phải thành một operation** trong class diagram.
:en
**Step 2: identify system objects.** The source is the **use case specification** (flows of events).
- **Every step in the "screenplay" must be performed by some object.** Create **boundary** and **control** objects when no domain object can do it.
- Draw a **sequence diagram for each important scenario**: **lifelines** reveal the objects, **messages** reveal their operations.

A **sequence diagram** shows how objects **interact over time** to realize one scenario. Main elements:

| Element | Meaning |
|---|---|
| **Lifeline** | A participant: actor, boundary, controller, entity object |
| **Message** | **Synchronous call**, **asynchronous message**, **return** |
| **Activation bar** | When an object is **executing** |
| **Combined fragment** | **alt** (if/else), **opt** (if), **loop**, **par** |

How to draw: take **one flow** from the use case spec, **one diagram per important scenario**; **every message should become an operation** in the class diagram.

@card 07#23 fig=sequence
:vi
Ví dụ use case **"Register for a course"**, luồng chính và một luồng phụ:
1. Student chọn môn, bấm Register trên **RegistrationUI**.
2. UI gọi `register(studentId, courseId)` trên **RegistrationController**.
3. Controller hỏi **Course** `hasFreeSeat()`, nhận về true/false.
4. Khung **alt**: **[seat available]** → tạo **Enrollment** bằng `create(studentId, courseId)` và trả *success*; **[course full]** → trả `error("Course is full")`.

Công cụ: **PlantUML, Mermaid, draw.io, StarUML**. Sơ đồ dạng **diagrams-as-code** lưu được **trong Git**.
:en
Example use case **"Register for a course"**, basic flow and one alternative flow:
1. The Student selects a course and clicks Register on **RegistrationUI**.
2. The UI calls `register(studentId, courseId)` on **RegistrationController**.
3. The controller asks **Course** `hasFreeSeat()` and gets true/false.
4. **alt** frame: **[seat available]** → create an **Enrollment** with `create(studentId, courseId)` and return *success*; **[course full]** → return `error("Course is full")`.

Tools: **PlantUML, Mermaid, draw.io, StarUML**. **Diagrams-as-code** can be versioned **in Git**.

@card 07#24
:vi
Ví dụ **"Student Management System"**, use case **Login**, scenario **Login failed**: giáo viên nhập username/password, phần mềm **mã hoá thông tin** (bước 4) rồi **kiểm tra hợp lệ** (bước 5), cuối cùng báo sai username/password.

Hai bước này **không domain object nào làm**, nên sinh ra **system object**:

| Bước | Object | Loại |
|---|---|---|
| 4 | **Encryptor** | System |
| 5 | **LoginAccount** | System |

Example **"Student Management System"**, use case **Login**, scenario **Login failed**: the teacher enters a username and password, the software **encrypts the data** (step 4) and **checks it** (step 5), then reports a wrong username/password.

**No domain object** performs those two steps, so they produce **system objects**:

| Step | Object | Type |
|---|---|---|
| 4 | **Encryptor** | System |
| 5 | **LoginAccount** | System |

@card 07#25
:vi
**Bước 3a: Tinh chỉnh class diagram.** Áp dụng luật hướng đối tượng:
- **Encapsulation** (luật hộp đen): **giấu dữ liệu, chỉ lộ operation**.
- Dữ liệu và hành vi dùng chung → **inheritance** (generalization).
- Cùng operation nhưng dữ liệu hay cách xử lý khác → **polymorphism**.

Thêm nữa: **mỗi message trong sequence diagram → một operation** của class; điền đủ **multiplicity, navigability, visibility**; kiểm tra theo nguyên tắc **low coupling, high cohesion**.
:en
**Step 3a: refine the class diagram.** Apply object-oriented rules:
- **Encapsulation** (black-box rule): **hide data, expose operations**.
- Shared data and behaviour → **inheritance** (generalization).
- Same operation, different data or processing → **polymorphism**.

Also: **every message in the sequence diagrams → an operation** of a class; complete **multiplicities, navigability and visibility**; check against **low coupling, high cohesion**.

@card 07#26 fig=order-state
:vi
**Bước 3b: Mô hình hoá object có vòng đời.** Object có **trường trạng thái** (order, booking, account) thì vẽ **state machine diagram**.
- Thành phần: **state**, **transition** dạng `event [guard] / action`, **trạng thái đầu** và **trạng thái cuối**.
- Ví dụ **Order**: Created —pay→ Paid —ship→ Shipped —deliver→ Delivered; Created —cancel→ Cancelled; Paid —cancel [before shipping] / refund→ Cancelled.

**Nó giúp class diagram thế nào:**
- **Mỗi event → một operation** của class: `pay()`, `ship()`, `deliver()`, `cancel()`.
- **Lộ ra transition còn thiếu và operation không hợp lệ**, ví dụ giao một đơn đã huỷ.
:en
**Step 3b: model objects with a life cycle.** Objects with a **status field** (order, booking, account) get a **state machine diagram**.
- Elements: **states**, **transitions** written `event [guard] / action`, **initial and final states**.
- Example **Order**: Created —pay→ Paid —ship→ Shipped —deliver→ Delivered; Created —cancel→ Cancelled; Paid —cancel [before shipping] / refund→ Cancelled.

**What it refines in the class diagram:**
- **Each event → an operation** of the class: `pay()`, `ship()`, `deliver()`, `cancel()`.
- **Reveals missing transitions and invalid operations**, e.g. shipping a cancelled order.

## 7.5 | Coupling, cohesion & SOLID | Coupling, cohesion & SOLID
@card 07#28
:vi
| | Định nghĩa | Mục tiêu |
|---|---|---|
| **Coupling** | Một module **phụ thuộc mạnh tới mức nào** vào module khác | **Low coupling**: phụ thuộc vào **interface**, truyền dữ liệu **tường minh**, tránh **trạng thái toàn cục dùng chung** |
| **Cohesion** | Các trách nhiệm **bên trong một module** gắn bó với nhau tới mức nào | **High cohesion**: **một module = một trách nhiệm rõ ràng** |

**Nguyên tắc khác:**
- **Encapsulation / information hiding**: giấu chi tiết bên trong sau một interface.
- **DRY** (Don't Repeat Yourself) · **KISS** (Keep It Simple) · **YAGNI** (You Aren't Gonna Need It).

**Low coupling + high cohesion → dễ sửa, dễ test, dễ dùng lại.**
:en
| | Definition | Aim |
|---|---|---|
| **Coupling** | **How strongly** one module depends on others | **Low coupling**: depend on **interfaces**, pass data **explicitly**, avoid **shared global state** |
| **Cohesion** | How closely the responsibilities **inside one module** belong together | **High cohesion**: **one module = one clear responsibility** |

**Other principles:**
- **Encapsulation / information hiding**: hide internal details behind an interface.
- **DRY** (Don't Repeat Yourself) · **KISS** (Keep It Simple) · **YAGNI** (You Aren't Gonna Need It).

**Low coupling + high cohesion → easier to change, test and reuse.**

@card 07#29
:vi
**SOLID**: 5 nguyên tắc thiết kế class.

| Nguyên tắc | Ý nghĩa | Dấu hiệu khi vi phạm |
|---|---|---|
| **S · Single Responsibility** | Một class chỉ có **một lý do để thay đổi** | **"God class"** làm mọi thứ |
| **O · Open/Closed** | **Mở để mở rộng, đóng để sửa đổi** | Thêm một loại mới là phải **sửa một switch lớn** |
| **L · Liskov Substitution** | **Subtype thay được cho base type** | Subclass ném lỗi **"not supported"** |
| **I · Interface Segregation** | **Nhiều interface nhỏ** tốt hơn một interface lớn | Class phải cài **method rỗng** |
| **D · Dependency Inversion** | **Phụ thuộc vào abstraction**, không vào class cụ thể | Business logic **tự tạo object database** |
:en
**SOLID**: five class design principles.

| Principle | Meaning | Symptom when violated |
|---|---|---|
| **S · Single Responsibility** | A class has **one reason to change** | A **"God class"** that does everything |
| **O · Open/Closed** | **Open for extension, closed for modification** | Adding a type means **editing a big switch** |
| **L · Liskov Substitution** | **Subtypes can replace their base type** | A subclass throws **"not supported"** |
| **I · Interface Segregation** | **Many small interfaces** over one large one | Classes implement **empty methods** |
| **D · Dependency Inversion** | **Depend on abstractions**, not concrete classes | Business logic **creates DB objects directly** |

## 7.6 | Design pattern | Design patterns
@card 07#30-31
:vi
**Design pattern** = **giải pháp đã được chứng minh** cho **một bài toán hay gặp**. Phân loại theo **mục đích** (Creational, Structural, Behavioral) và **phạm vi** (class hay object).

**Danh mục GoF:**

| Nhóm | Trả lời câu hỏi | Pattern |
|---|---|---|
| **Creational** | **Object được tạo ra thế nào?** | Factory Method, Abstract Factory, Builder, Prototype, Singleton (+ Object Pool) |
| **Structural** | **Class và object được ghép lại thế nào?** | Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy |
| **Behavioral** | **Object tương tác và chia trách nhiệm thế nào?** | Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method (+ Null Object) |

Lời khuyên trên slide: **nắm mục đích của từng nhóm**, học kỹ vài pattern thay vì thuộc hết tên.
:en
A **design pattern** = a **proven solution** to a **common problem**. Patterns are grouped by **purpose** (Creational, Structural, Behavioral) and by **scope** (classes or objects).

**The GoF catalog:**

| Purpose | Question it answers | Patterns |
|---|---|---|
| **Creational** | **How are objects created?** | Factory Method, Abstract Factory, Builder, Prototype, Singleton (+ Object Pool) |
| **Structural** | **How are classes and objects composed?** | Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy |
| **Behavioral** | **How do objects interact and share responsibilities?** | Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method (+ Null Object) |

The slide's advice: **know the purpose of each group** and learn a few patterns well rather than memorizing every name.

@card 07#32
:vi
**Pattern nào cho bài toán nào:**

| Bài toán trong dự án | Pattern |
|---|---|
| Nhiều luật giá/giảm giá khác nhau cho vé | **Strategy** |
| Tạo đúng object phương thức thanh toán (thẻ, ví điện tử, chuyển khoản) | **Factory Method** |
| Báo email, SMS và app khi booking thay đổi | **Observer** |
| Dùng API bên thứ ba có interface khác | **Adapter** |
| Một lối vào đơn giản cho một subsystem phức tạp | **Facade** |
| Một object cấu hình dùng chung | **Singleton** (cẩn thận: **khó test**) |

**Pattern là từ vựng, không phải mục tiêu**: chỉ dùng khi bài toán thật sự xuất hiện.
:en
**Which pattern for which problem:**

| Problem in a project | Pattern |
|---|---|
| Different pricing/discount rules for tickets | **Strategy** |
| Create the right payment method object (card, e-wallet, bank transfer) | **Factory Method** |
| Notify email, SMS and app when a booking changes | **Observer** |
| Use a third-party API with a different interface | **Adapter** |
| A simple entry point to a complex subsystem | **Facade** |
| One shared configuration object | **Singleton** (use carefully: **hurts testability**) |

**Patterns are a vocabulary, not a goal**: apply one only when the problem appears.

@card 07#33
:vi
**Ví dụ Strategy pattern**
- **Bài toán:** giá vé phụ thuộc loại khách: sinh viên, người cao tuổi, thành viên… nên trong `Booking` có chuỗi **if/else ngày càng dài**.
- **Giải pháp:** interface **`PricingStrategy`** có `calculate(basePrice)`; các class `StudentPricing`, `SeniorPricing`, `MemberPricing` cài interface đó; `Booking` **giữ một `PricingStrategy`** và gọi `calculate()`.
- **Lợi ích:** luật mới = **class mới**, **không sửa `Booking`** (đúng **Open/Closed**); từng luật **unit test riêng** được.
:en
**Example: the Strategy pattern**
- **Problem:** ticket price depends on the customer type: student, senior, member… giving a **growing if/else chain** inside `Booking`.
- **Solution:** an interface **`PricingStrategy`** with `calculate(basePrice)`; `StudentPricing`, `SeniorPricing`, `MemberPricing` implement it; `Booking` **holds a `PricingStrategy`** and calls `calculate()`.
- **Benefits:** a new rule = **a new class**, **`Booking` is not changed** (**Open/Closed**); each rule can be **unit-tested on its own**.

@card 07#32-33 real
:vi
BadminBookingHub có giá sân khác nhau theo **giờ cao điểm**, ngày thường hay cuối tuần: đúng chỗ dùng **Strategy**. Còn việc báo cho Player và Staff khi một booking bị huỷ là bài toán của **Observer**.
:en
BadminBookingHub prices courts differently for **peak hours**, weekdays and weekends: a natural fit for **Strategy**. Notifying the Player and Staff when a booking is cancelled is an **Observer** problem.

## 7.7 | Thiết kế dữ liệu | Data design
@card 07#35
:vi
**Chọn nơi lưu dữ liệu:**

| | **File system** | **Database system** |
|---|---|---|
| Cách lưu | Lưu trong **file**, **tự tổ chức** cấu trúc file | Lưu trong **bảng**, dùng **DBMS** |
| ✔ | **Đơn giản, nhanh** | **Quản lý dữ liệu lớn hiệu quả** |
| ✘ | **Khó quản lý dữ liệu lớn** | **Phức tạp hơn** để cài đặt và quản trị |

Lựa chọn khác: **NoSQL** (document, key-value, graph) cho **schema linh hoạt** hoặc **quy mô cực lớn**.
:en
**Choosing data storage:**

| | **File system** | **Database system** |
|---|---|---|
| How | Data in **files**, **self-organized** file structures | Data in **tables**, managed by a **DBMS** |
| ✔ | **Simple, fast** | **Manages large data efficiently** |
| ✘ | **Hard to manage large data** | **More complex** to set up and administer |

Other option: **NoSQL** (document, key-value, graph) for **flexible schemas** or **massive scale**.

@card 07#36-37
:vi
**Ánh xạ design class sang nơi lưu:** mỗi **persistent (entity) class → một đơn vị lưu**: **một file** (file system) hoặc **một bảng** (database). Attribute → **field/column**; **object identity → primary key**; association → **foreign key** hoặc **junction table**.

| Phần tử class diagram | Thiết kế quan hệ | Ví dụ |
|---|---|---|
| **Entity class** | **Bảng**; attribute → cột; thêm **primary key** | Student → `student(id PK, name, dob)` |
| **Association 1 – n** | **Foreign key ở phía "n"** | Class 1 – n Student → `student.class_id FK` |
| **Association n – n** | **Junction table** có 2 foreign key | `enrollment(student_id, course_id)` |
| **Attribute của liên kết** (association class) | **Cột thêm trong junction table** | `enrollment.grade`, `enrollment.date` |
| **Composition** | **FK NOT NULL + ON DELETE CASCADE** | Order ◆— OrderLine |
| **Generalization** | **Một bảng cho cả cây, mỗi class một bảng, hoặc mỗi class cụ thể một bảng** | Person → Student, Lecturer |
:en
**Mapping design classes to storage:** each **persistent (entity) class → one storage unit**: **one file** (file system) or **one table** (database). Attributes → **fields/columns**; **object identity → primary key**; associations → **foreign keys** or **junction tables**.

| Class diagram element | Relational design | Example |
|---|---|---|
| **Entity class** | A **table**; attributes → columns; add a **primary key** | Student → `student(id PK, name, dob)` |
| **1 – n association** | **Foreign key on the "many" side** | Class 1 – n Student → `student.class_id FK` |
| **n – n association** | **Junction table** with two foreign keys | `enrollment(student_id, course_id)` |
| **Attributes of a link** (association class) | **Extra columns in the junction table** | `enrollment.grade`, `enrollment.date` |
| **Composition** | **FK NOT NULL + ON DELETE CASCADE** | Order ◆— OrderLine |
| **Generalization** | **One table per hierarchy, per class, or per concrete class** | Person → Student, Lecturer |

@card 07#40
:vi
**Checklist thiết kế CSDL quan hệ:**
- Mọi bảng có **primary key**; quan hệ dùng **foreign key**.
- **Chuẩn hoá tới 3NF** để tránh dư thừa và **update anomaly**; chỉ **denormalize** khi **đã chứng minh** cần cho hiệu năng.
- Chọn **đúng kiểu dữ liệu**; dùng ràng buộc **NOT NULL, UNIQUE, CHECK**.
- Thêm **index** cho cột hay tìm kiếm và join.
- **Đặt tên nhất quán**, ví dụ snake_case, tên bảng số ít.
- **Lưu mật khẩu dạng hash**; thu thập ít và bảo vệ **dữ liệu cá nhân**.
- Quản lý thay đổi schema bằng **migration script trong Git**.
:en
**Relational database design checklist:**
- Every table has a **primary key**; relationships use **foreign keys**.
- **Normalize to 3NF** to avoid redundancy and **update anomalies**; **denormalize** only for **proven** performance needs.
- Choose **correct data types**; use **NOT NULL, UNIQUE and CHECK** constraints.
- Add **indexes** for frequent search and join columns.
- **Consistent naming**, e.g. snake_case, singular table names.
- **Store passwords as hashes**; minimize and protect **personal data**.
- Manage schema changes with **migration scripts in Git**.
